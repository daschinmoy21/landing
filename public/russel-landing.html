Why Russel

Isolation when you want it, speed when you don't.

Not every service needs a hardware boundary. Russel lets you pick container or microVM per deploy — and switch between them with one config line and zero downtime. A CVE on a container runtime? Russel auto-promotes it to a hardened microVM before you even read the advisory.

01 — Dual runtime

Container or microVM. One config line to flip.

Every service gets a runtime field in its config: container for fast Podman-based deploys, microvm for hardware isolation via Cloud Hypervisor + KVM. Change the field, re-deploy — zero downtime, no re-architecture. If a CVE hits your container runtime, Russel auto-switches the service to a microVM so the boundary is already hardened by the time you check your inbox.

PodmanCloud HypervisorZero-downtime switch
02 — Immutable builds

Content-addressed. Zero drift.

Builds are Nix. Content-addressed, fully deterministic: the same inputs always produce the same store path, on your laptop, the build server, and the deploy box. No “works on my machine,” no surprise drift between staging and prod. Every deploy is immutable — the hash proves exactly what ran, and the past is never overwritten.

NixContent-addressedDedupZero drift
03 — Ownership

Self-hosted. No vendor lock-in.

Russel runs on hardware you already own — a homelab box, a rented bare-metal server, a rack in a colo. No control plane you can’t see, no egress billed by the gigabyte, no platform deprecating your region. You hold the root.

How it works

From repo to serving in five steps.

One CLI command drives the whole path — the CLI streams progress to your terminal over HTTP/NDJSON. The runtime field in your config picks container or microVM; swap it any time and re-deploy with zero downtime.

01

Clone

Pull your repo. Russel reads the Russelfile.toml (migrating to YAML).

02

nix build

Reproducible build produces a single content-addressed store path.

→
03

runtime dispatch

Config field runtime = "microvm" or "container" picks the engine — Podman or Cloud Hypervisor.

→
04

boot

Cloud Hypervisor for microVMs (2 MB initramfs, no systemd); Podman for fast container starts.

→
05

serve

Networking wired via iptables/socat. Your service is live — immutable and zero-drift.

Quick start

Zero to deployed in three commands.

1

Install Russel

From source with Nix — it pins its own toolchain. nix profile install into your PATH.

2

Grab an app

Any repo with a Russelfile.toml. git clone your service and cd in.

3

Deploy

russel deploy builds, packs the initramfs, boots the microVM, and serves. One command, NDJSON streamed to your terminal.

quickstart
# 1 · install
$ nix profile install github:russel/russel
# 2 · grab an app
$ git clone git@github.com:you/my-app && cd my-app
# 3 · deploy

Architecture

Three moving parts, no surprises.

The CLI talks to a local control plane over HTTP/NDJSON. The control plane boots the microVM directly on Cloud Hypervisor — no containerd in the middle, no NixOS guest.
